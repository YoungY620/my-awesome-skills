# 问题诊断标准

本文是问题诊断的唯一规则源。目标是让诊断过程可执行、可回退、可验证，
避免把局部检查、直接报错或一次成功误判成完整结论。

## 一、不可跳过的原则

1. 先固定原始问题和验收判据，再检查实现。
2. 根因必须同时解释失败现象、case 选择性和时间或数量分布。
3. 未检查的路径属于未知，不属于已排除。
4. 每个关键结论都需要直接证据、判别实验或明确标注的证据边界。
5. 没有判别性证据不修复；原始失败场景未复验不宣布恢复。
6. 证据不足时返回假设或插桩阶段，不用更多推测代替取证。
7. 诊断和修复分开授权；只要求诊断时不修改实现。

## 二、统一诊断闭环

### D01 — 固定原始现场与验收判据

记录期望行为、实际行为、影响范围、首次发生时间和原始报错。保存 job、
attempt、request ID、日志、附件、配置和版本。明确要回答的是原始执行失败、
重试未运行、平台状态异常、进程退出、评分异常还是交付失败。

验收判据在排查前定义，至少包括需要恢复的 case、必须产生的产物、平台终态、
评分或业务结果，以及后续执行是否恢复。

### D02 — 还原时间线与责任边界

划分启动、执行、截断、清理、收集、上传、上报、重试和销毁阶段，找到最后
正常节点与首个异常节点。每个阶段标明输入、输出、责任组件和可观察完成标志。

### D03 — 描述异常分布

同时比较失败和成功集合，检查 case 是否重合、耗时是否集中、实例是否同步
死亡、数值是否等于超时或资源上限，以及故障是否与并发、版本、平台或时间窗口
相关。分布是独立证据，不是等待解释的细节。

### D04 — 建立假设全集与证据覆盖表

假设至少覆盖：任务内容、Agent 客户端、完整请求、环境初始状态、基础资源、
网络与凭证、平台调度、生命周期、观测链路和恢复逻辑。对每项标记直接证据、
推断、未检查，以及能够推翻它的观测。

### D05 — 按假设插桩并自动复现

优先复用现有日志、trace 和产物；信息不足时增加有界、可移除的临时插桩。
每条日志必须对应一个假设，记录变量值、执行路径、时间、关联 ID 和状态转换，
不得记录密钥或无关敏感数据，也不得显著改变被测行为。

用测试、受控 Job、脚本或影子任务还原原始条件。证据不足时补充假设或插桩；
复现失败时修正复现条件；不得直接跳到修复。

### D06 — 形成因果链并实施定向修复

区分根因、触发条件、放大器、次生故障和恢复失败。只修改证据指向且属于当前
授权范围的环节。修复新增的逻辑也进入故障树和回归范围。

### D07 — 全量复验、清理与报告

重跑原始失败集合和完整生产链路，检查日志、附件、评分、最终产物、平台状态
和后续执行。移除临时插桩、探针和脚本，保留必要的长期观测。按已确认、部分
确认、尚未确认报告，不扩大证据范围。

## 三、八类场景 playbook

### S01 — 初步检查声称无问题或无法复现

**场景共性**：本机通过、简单探针成功、没有错误日志、进程存活或新一轮成功，
被扩大成整个系统正常。本质是观察覆盖小于故障覆盖。

**必须执行**：

1. 先取得原始失败证据，不用新一轮成功覆盖旧失败。
2. 列出本次检查覆盖的代码、配置、客户端、完整请求、环境、时间和平台。
3. 对照原始条件逐项补齐未覆盖变量。
4. 检查观测系统是否漏采、截断、延迟或只反映控制面。
5. 原始异常未解释前，保持问题打开。

**闭环判据**：只能声称在明确范围内未发现；原始故障路径被覆盖后，才能讨论
问题是否存在。

### S02 — 找到浅层直接原因

**场景共性**：把报错名称或异常阶段当根因，例如 tar 失败、网络断流、runner
收尾异常、重试未执行。它说明哪里失败，却没有说明为何进入该状态。

**必须执行**：

1. 从最终失败向前逐环追问原因，直到可干预的责任边界。
2. 标明根因、触发条件、放大器、次生故障和恢复失败。
3. 检查当前结论回答的是原始故障，还是重试、上报或评分问题。
4. 验证针对该机制的干预能够消除故障。

**闭环判据**：结论同时解释直接报错、形成过程和现有防护为何未能阻止故障。

### S03 — 失败集合或数字呈异常规律

**场景共性**：case 完全重合、耗时高度一致、多实例同步死亡，或数值恰好等于
超时、TTL、重试次数和资源上限，通常意味着共享条件或确定性机制。

**必须执行**：

1. 同时建立失败和成功集合。
2. 比较任务内容、镜像、依赖、资源、客户端、并发、时间、版本和平台节点。
3. 把解释集合选择性和数字分布作为假设的硬约束。
4. 对共同条件做最小实验，并覆盖整个失败集合。
5. 新解释无法说明 case 选择性时，继续追查。

**闭环判据**：同时回答为什么失败、为什么是这些 case、为什么以这种时间或
数量分布出现。

### S04 — 不同实例共享同一症状名称

**场景共性**：卡死、超时、断流或环境失败只是症状，可能由代码、外部服务、
资源、平台或观测问题分别造成。

**必须执行**：

1. 为每个实例记录最后事件、停滞时长、CPU、连接、产物、退出码和恢复过程。
2. 按机制而非错误文案聚类。
3. 每类分别建立因果链、修复项和验收指标。
4. 无法归类的实例保留为未解决。
5. 按某类故障零复发报告，不把局部修复写成全部恢复。

**闭环判据**：每个实例都有归属，每类都有独立证据与验证，没有隐藏的剩余组。

### S05 — 对照组成功但并不等价

**场景共性**：另一个 Agent、直接 prompt、本机、新沙箱或低并发实验成功，
却改变了客户端、完整请求、初始状态、操作系统、负载或平台窗口。

**必须执行**：

1. 核对代码配置、Agent、客户端、完整请求、镜像初始状态、运行时、URL、
   凭证、路由、并发、账户压力、时间窗口和平台健康。
2. 每次只改变一个待验证变量。
3. 随机或负载相关故障增加样本量和持续时间。
4. 平台噪声污染实验时，标记为无判别力。
5. 结论只外推到已覆盖条件。

**闭环判据**：对照之间唯一实质差异就是待验证变量。

### S06 — 全新环境或基础资源异常

**场景共性**：新实例只有身份是新的，文件系统、快照、依赖和资源未必干净；
权限、网络或凭据报错也可能是资源不足的次生症状。

**必须执行**：

1. 检查出生时的文件、进程、挂载、证书、依赖和初始化标记。
2. 检查磁盘、内存、CPU、进程数、文件描述符和残留锁。
3. 与成功环境比较实际状态，不只比较声明配置。
4. 将可确认的故障层与尚未查明的污染或构建来源分开报告。

**闭环判据**：环境实际状态能够解释故障；新实例、重试或权限表象不再被当作
根因证据。

### S07 — 主流程成功但收尾或交付失败

**场景共性**：业务执行完成，但日志上传、产物收集、脱敏、审计、状态上报或
清理失败；控制面、业务结果和交付结果不一致。

**必须执行**：

1. 为生命周期每个阶段定义输入、输出、责任组件和完成标志。
2. 检查进程树、后台任务、共享文件和写入者，必要时设置收集前静止点。
3. 检查观测与交付链路本身，不用其状态替代实际执行证据。
4. 分别验证业务结果、产物完整性、平台终态和下一轮执行。

**闭环判据**：主任务、产物上传、状态结算和后续任务均正常。

### S08 — 修复或重试后仍失败

**场景共性**：重试复用旧状态，同一规则存在多份拷贝，修复引入新缺陷，或恢复
探测错误推进状态机。

**必须执行**：

1. 区分崩溃恢复、继续执行、重放记录和用户显式重跑。
2. 显式重跑创建新执行代次，不按旧终态跳过。
3. 全局搜索代码、脚本、审计、提示词和文档中的同义规则。
4. 将修复新增逻辑纳入回归测试。
5. 恢复探测只有确认成功后才推进；失败探测不能解除冷却。
6. 连续观察后续真实轮次，独立核实新报警。

**闭环判据**：重试产生真实新执行，同义规则一致，完整管线通过，后续报警也
得到独立验证。

## 四、对照实验与插桩检查

### 对照等价条件

代码和配置、Agent 和客户端、完整请求、镜像及初始状态、操作系统和运行时、
URL 和路由、凭证、并发和账户压力、时间窗口、平台健康必须逐项核对。直接
prompt、另一个客户端或另一操作系统成功，不能自动构成原链路的反证。

### 最小实验

每次只改变一个变量，并预先定义成功与失败判据。典型边界包括默认配置与显式
配置、小与大输入、低与高并发、原与扩大后的生命周期、原始与修复版本。实验
结果只适用于覆盖的客户端、协议和生产路径。

### 插桩纪律

先复用现有观测，再添加临时插桩；插桩必须可区分竞争假设、可限制体量、可
移除且不泄露敏感信息。跨组件调用使用统一关联 ID。插桩改变了时序或行为时，
该结果不能直接用于证明原系统行为。

## 五、结论与验收语言

- **当前范围内未发现**：列明检查范围和未覆盖路径，不写没有问题。
- **根因已确认**：原因解释主要现象、数字分布和完整因果链，并有复现、消除
  或同等强度现场证据。
- **系统已恢复**：原始失败集合在完整生产链路通过，产物、状态和后续执行均
  正常，不写单次探针成功即恢复。
- **部分确认**：分别列出已经验证的机制、受噪声影响的实验和剩余异常。

## 六、持续学习

1. 只记录用户明确提出的纠偏、否决和稳定原则；助手建议、review bot 意见和
   助手修复汇报不算用户偏好。
2. 每条记录包含日期、来源、关联规则、用户原话或准确近义表述、沉淀动作。
3. 新场景先进入候选；两个独立任务或会话重复出现时更新现有规则与强调次数，
   不复制近似条目。用户明确表述为通用原则时可直接纳入核心规则。
4. 用户修正或撤回时，更新当前定义和边界，保留仍有效的部分。
5. 一次性项目约束不推广成通用禁令；规则、模板和入口文件不重复维护同一内容。
6. 记录不包含个人姓名、私有环境、绝对开发路径、密钥、内部任务标识或不可
   公开的项目细节。

## 七、范围边界

- 诊断不等同于修复；未获修复授权时只报告原因、证据和建议。
- 不绕过安全、权限、成本控制或生产保护来完成复现。
- 高风险、不可逆或影响外部系统的实验必须先取得明确授权。
- 已有同等证据时不重复昂贵实验；需要补充的是缺失证据，不是重复次数。
